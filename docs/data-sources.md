# RelayOps 多数据源设计

> 状态：已确认
>
> 适用范围：RelayOps 后端本地采集、Sub2API 外部只读数据接入
>
> 最后更新：2026-11-06

## 1. 文档目标

本文档约束 RelayOps 后端的数据源边界、数据访问方式、事务规则、同步策略、实时查询策略和故障降级方式。

后续采集策略、预警、通知、外部数据查询等实现必须以本文档为前提。任何代码不得绕过多数据源边界直接访问数据库。

## 2. 已确认的架构决策

1. 项目使用两个 PostgreSQL 数据源：
   - 本地主库：保存 RelayOps 自己的业务数据；
   - Sub2API 外部库：只读，用于关联查询和预警所需数据。
2. 外部库确定只有一个。
3. 外部库使用已有的只读账号。
4. 外部数据存在两种访问模式：
   - 定时同步：批量读取外部数据，处理后保存到本地库；
   - 实时读取：页面、预警或机器人查询时按需读取外部库。
5. 本地主库使用 MyBatis-Plus。
6. 本地主库执行 Flyway。
7. 本地主库拥有读写权限，并拥有默认事务管理器。
8. 外部 Sub2API 库不执行 Flyway。
9. 外部 Sub2API 库不注册本地 MyBatis-Plus Mapper。
10. 外部 Sub2API 库不参与本地默认事务。
11. 外部 Sub2API 库默认关闭；未配置时应用必须正常启动。
12. 不允许跨数据源事务，不允许使用分布式事务。

## 4. 为什么第二个数据源不使用 MyBatis-Plus

Sub2API 数据库属于另一个系统，RelayOps 只是只读使用方。

不建议在外部库使用 MyBatis-Plus 的原因：

1. 外部表结构由 Sub2API 项目维护，不应在 RelayOps 中建立长期 Entity 负担。
2. 大部分查询是关联、聚合、时间窗口和游标分页，不是标准 CRUD。
3. 两套 MyBatis-Plus `SqlSessionFactory`、Mapper 扫描和事务管理器会增加配置复杂度。
4. Mapper 扫描范围写错时，可能把外部表查询错误地路由到主库。
5. 外部库只读，不需要 MP 的插入、更新、删除和乐观锁能力。
6. 原项目已经采用独立 JDBC 只读入口，行为明确，迁移风险更低。

因此：

- MyBatis-Plus 只服务本地主库；
- Sub2API 外部库使用独立只读的 `JdbcTemplate`；
- 外部查询结果必须映射为明确的只读 record 或只读项目模型；
- 外部表不得直接暴露到 Controller 或领域对象。

如果未来外部库出现大量、稳定的实体 CRUD 场景，再单独评估 MyBatis-Plus；当前不引入。

## 5. 为什么外部数据源不注册为普通 DataSource Bean

外部数据源建议由 `Sub2ReadOnlyJdbc` 这样的普通组件持有独立连接池，而不是直接注册为 `DataSource` 类型的 Spring Bean。

原因：

1. 主库已经有 MyBatis-Plus、Flyway 和默认事务管理器。
2. 再注册一个 `DataSource` Bean 会增加自动配置注入歧义。
3. Flyway 自动配置可能按类型选择数据源，存在把迁移执行到外部库的风险。
4. 外部库是可选依赖，未配置时不应影响应用启动。
5. 外部库只需要只读查询，不需要参与 Spring 的事务代理。
6. 独立包装类可以统一管理懒初始化、查询超时、连接池关闭和失败冷却。

推荐行为：

- `primaryDataSource` 正常运行，作为主库。
- `Sub2ReadOnlyJdbc` 是普通 `@Component`。
- 外部连接池在第一次查询时懒初始化。
- 外部连接池设置 `readOnly=true`。
- 外部连接池初始化失败不阻止应用启动。
- 外部查询失败时进入短时间冷却窗口，避免每次请求都等待超时。
- 外部连接池在应用关闭时主动关闭。

外部连接池是“数据源能力”，但不以 `DataSource` Bean 的形式暴露给 Spring 自动配置。

## 6. 模块和包边界

### 6.1 本地主库访问

```text
com.relayops.upstream.adapter.out.persistence
├── entity
├── mapper
└── repository

com.relayops.monitoring.adapter.out.persistence
com.relayops.notification.adapter.out.persistence
com.relayops.operations.adapter.out.persistence
com.relayops.scheduling.adapter.out.persistence
```

规则：

- Entity 只属于本地主库。
- Mapper 只使用主库。
- Repository 只面向本地主库。
- `@Mapper` 必须位于明确的主库 Mapper 包中。
- 默认 `@Transactional` 只用于本地主库事务。

### 6.2 外部只读库访问

```text
com.relayops.integration.sub2db
├── Sub2ReadOnlyJdbc
├── Sub2ReadOnlyException
├── Sub2ReadOnlyProperties
├── user/
│   └── Sub2UserReader
├── usage/
│   └── Sub2UsageLogReader
├── group/
│   └── Sub2GroupReader
├── order/
│   └── Sub2OrderReader
├── error/
│   └── Sub2ErrorReader
├── proxy/
│   └── Sub2ProxyReader
└── monitor/
    └── Sub2ChannelMetricsReader
```

规则：

- 外部 SQL 只能出现在 `integration.sub2db`。
- 外部 Reader 不允许写数据库。
- 外部 Reader 不允许引用本地 Entity、Mapper 或 Repository。
- 外部 Reader 返回只读 record、值对象或明确的查询结果。
- 外部 Reader 不抛出泄露连接信息、SQL 参数和密码的异常。
- 业务模块依赖外部查询 Port，不直接依赖 `JdbcTemplate`。

### 6.3 业务模块依赖方向

```text
upstream.application
    -> upstream.contract
    -> integration.sub2db Port
    -> primary persistence Port

monitoring.application
    -> monitoring.contract
    -> upstream.contract
    -> integration.sub2db Port
    -> primary persistence Port

notification.application
    -> upstream/monitoring/operations.contract
    -> primary notification persistence

integration.sub2db
    -> 外部只读 JdbcTemplate
    -> shared
```

禁止：

- `integration.sub2db` 引用本地 Mapper；
- `upstream.adapter.out.persistence` 引用外部 JdbcTemplate；
- Controller 直接调用外部 Reader；
- 领域模型直接持有 `JdbcTemplate`、`HikariDataSource` 或 SQL 字符串；
- 通知模块直接读取外部库后再写本地库并在同一事务中提交。

## 7. 数据所有权和访问矩阵

| 数据类别 | 数据归属 | 原系统 | 本地保存 | 访问方式 | 访问模式 |
|---|---|---|---|---|---|
| 平台配置 | 本地主库 | RelayOps | 是 | MyBatis-Plus | 读写 |
| 账号与凭证 | 本地主库 | RelayOps | 是 | MyBatis-Plus | 读写 |
| 采集批次 | 本地主库 | RelayOps | 是 | MyBatis-Plus | 读写 |
| 采集快照 | 本地主库 | RelayOps | 是 | MyBatis-Plus | 读写 |
| 预警规则 | 本地主库 | RelayOps | 是 | MyBatis-Plus | 读写 |
| 预警状态 | 本地主库 | RelayOps | 是 | MyBatis-Plus | 读写 |
| 同步游标 | 本地主库 | RelayOps | 是 | MyBatis-Plus | 读写 |
| 同步执行记录 | 本地主库 | RelayOps | 是 | MyBatis-Plus | 读写 |
| 通知配置 | 本地主库 | RelayOps | 是 | MyBatis-Plus | 读写 |
| 平台用户 | 外部库 | Sub2API | 按需镜像/缓存 | `JdbcTemplate` | 只读 |
| 用户用量日志 | 外部库 | Sub2API | 是，按游标同步 | `JdbcTemplate` | 只读 |
| 分组与倍率 | 外部库 | Sub2API | 按需同步/缓存 | `JdbcTemplate` | 只读 |
| 账号分组关系 | 外部库 | Sub2API | 按需同步/缓存 | `JdbcTemplate` | 只读 |
| 用户订阅 | 外部库 | Sub2API | 按需缓存 | `JdbcTemplate` | 只读 |
| API Key 元数据 | 外部库 | Sub2API | 按需缓存 | `JdbcTemplate` | 只读 |
| 支付订单 | 外部库 | Sub2API | 默认不落本地 | `JdbcTemplate` | 实时只读 |
| 运维错误日志 | 外部库 | Sub2API | 默认不落本地 | `JdbcTemplate` | 实时只读 |
| 代理状态 | 外部库 | Sub2API | 按需缓存 | `JdbcTemplate` | 定时/实时只读 |
| 渠道监控指标 | 外部库 | Sub2API | 按需同步 | `JdbcTemplate` | 定时只读 |

说明：

- “本地保存”表示是否需要在 RelayOps 主库落一份数据。
- 不是所有外部表都需要镜像。只为预警、历史分析和稳定性需要的字段落本地。
- 外部库是事实来源，本地镜像必须记录同步时间和同步游标。
- 本地预警状态永远以本地主库为准，不能把外部库当预警状态库。

## 8. 外部 Sub2API 数据范围

以下范围来自现有功能，迁移时应逐项确认，不要一次性复制全部表。

### 8.1 平台用户

主要表：

- `public.users`

用途：

- 邮箱、用户名、数字 ID 与 RelayOps 用户或 QQ 用户关联；
- 平台用户身份识别；
- 余额、冻结余额、累计充值查询；
- 预警关联；
- 权限和分组判断。

读取要求：

- 必须过滤 `deleted_at IS NULL`；
- 不读取密码哈希、TOTP 密钥等敏感字段；
- 只选择业务需要的列；
- 用户查询使用短超时；
- 邮箱查询应使用大小写不敏感匹配，但参数必须绑定，禁止字符串拼接；
- 用户查询逻辑应使用明确索引，至少验证 `email`、`username`、`id` 的查询计划。

### 8.2 用量日志

主要表：

- `usage_logs`

用途：

- 号池/账号用量；
- API Key 用量；
- token、缓存、成本、延迟统计；
- 用量趋势和预警。

重点字段：

- `id`
- `account_id`
- `request_id`
- `api_key_id`
- `model`
- `created_at`
- `first_token_ms`
- `duration_ms`
- `input_tokens`
- `output_tokens`
- `cache_read_tokens`
- `cache_creation_tokens`
- `total_cost`
- `actual_cost`

同步策略：

- 使用 `id > lastId` 做真增量；
- 只同步受监控的 `account_id` 集合；
- 按 `id` 升序；
- 单批建议 1000～2000 条；
- 单轮最多处理若干批，避免停机后一次性拉爆；
- 首次启用时先取当前 `MAX(id)` 作为初始游标，默认不回灌全部历史；
- 是否回灌历史必须单独配置，不能默认全量扫描。

注意：

- `usage_logs` 的 token 字段在不同 Sub2API 版本中可能是 `int4` 或 `int8`，读取时应通过 `Number` 兼容，不能强制按单一类型读取。
- 汇总查询和明细查询必须分开。
- 日期范围统一使用左闭右开：`created_at >= from AND created_at < to`。

### 8.3 分组和渠道倍率

主要表：

- `groups`
- `account_groups`
- 可能使用 `user_allowed_groups`、`user_subscriptions`

用途：

- 账号所属分组；
- 分组倍率；
- 渠道可见性和订阅判断；
- 成本影响预警。

规则：

- 过滤软删除数据；
- 账号与分组可能是多对多；
- 倍率以 `groups.rate_multiplier` 为准；
- 不要把“账号倍率”和“分组倍率”混在同一口径；
- 需要批量查询时限制 `IN` 列表大小，避免生成超大 SQL；
- 查询结果应缓存或定时同步，避免每个页面请求重复关联查询。

### 8.4 API Key

主要表：

- `api_keys`
- `usage_logs`

用途：

- Key 与用户、账号关联；
- Key 用量；
- 异常 Key 或停用 Key 检测；
- 预警关联。

规则：

- 不读取明文密钥；
- 只读取 ID、名称、状态、所属用户、创建/失效时间等必要字段；
- Key 的用量从 `usage_logs` 聚合；
- 对外返回前必须脱敏。

### 8.5 支付订单

主要表：

- `public.payment_orders`

用途：

- 用户消费和充值分析；
- 异常订单或退款预警；
- 余额/消费关联。

规则：

- 使用 `user_id + created_at` 过滤；
- 时间窗左闭右开；
- 明细必须设置 `LIMIT`；
- 汇总单独查询，避免明细被 `LIMIT` 截断后汇总不完整；
- 默认实时读取，不落本地；只有预警或历史分析需要时才落本地。

### 8.6 错误和运维日志

主要表：

- `ops_error_logs`
- `ops_system_logs`
- `ops_ingress_reject_aggregates`

用途：

- 错误诊断；
- 错误聚合和预警；
- 请求链路追踪；
- 上游异常分析。

规则：

- 实时查询应有严格时间窗口；
- 默认只读最近一段时间；
- 必须限制返回行数；
- 不返回敏感请求体、密码、Token；
- 日志查询失败不能阻塞主业务；
- 高频错误查询应增加缓存或本地聚合。

### 8.7 代理和渠道监控

主要表：

- `proxies`
- `channel_monitor_v2_metrics_1m`
- 关联 `groups`

用途：

- 代理到期预警；
- 渠道健康状态；
- 渠道倍率和状态变化；
- 运维预警。

规则：

- 渠道指标适合定时同步或短周期轮询；
- 代理到期可以低频查询；
- 页面增强数据使用短超时；
- 外部数据失败时返回空增强数据，不阻塞核心页面。

## 9. 配置设计

### 9.1 主库配置

沿用 Spring Boot 标准配置：

- `spring.datasource.url`
- `spring.datasource.username`
- `spring.datasource.password`
- `spring.datasource.hikari.*`
- `spring.flyway.*`

主库必须是默认数据源和默认事务数据源。

### 9.2 外部只读库配置

建议使用独立前缀：

```yaml
relay-ops:
  datasource:
    sub2-read-only:
      enabled: ${SUB2API_DB_ENABLED:false}
      url: ${SUB2API_DB_URL:}
      username: ${SUB2API_DB_USERNAME:}
      password: ${SUB2API_DB_PASSWORD:}
      connect-timeout: ${SUB2API_DB_CONNECT_TIMEOUT:5s}
      query-timeout: ${SUB2API_DB_QUERY_TIMEOUT:30s}
      realtime-query-timeout: ${SUB2API_DB_REALTIME_QUERY_TIMEOUT:3s}
      maximum-pool-size: ${SUB2API_DB_POOL_SIZE:2}
      minimum-idle: ${SUB2API_DB_MIN_IDLE:1}
      batch-size: ${SUB2API_DB_BATCH_SIZE:2000}
      max-batches-per-run: ${SUB2API_DB_MAX_BATCHES_PER_RUN:20}
      unavailable-cooldown: ${SUB2API_DB_UNAVAILABLE_COOLDOWN:30s}
      realtime-max-rows: ${SUB2API_DB_REALTIME_MAX_ROWS:500}
```

配置说明：

| 配置 | 含义 | 建议初始值 |
|---|---|---|
| `enabled` | 是否启用外部库 | `false` |
| `url` | 外部只读 JDBC 地址 | 不写入仓库 |
| `username` | 只读账号 | 不写入仓库 |
| `password` | 只读密码 | 不写入仓库 |
| `connect-timeout` | 建立连接超时 | 5 秒 |
| `query-timeout` | 批量查询默认超时 | 30 秒 |
| `realtime-query-timeout` | 页面/实时查询超时 | 2～3 秒 |
| `maximum-pool-size` | 外部连接池上限 | 2～4 |
| `minimum-idle` | 外部连接池保底连接 | 1 |
| `batch-size` | 游标批量大小 | 1000～2000 |
| `max-batches-per-run` | 单轮最大批数 | 10～20 |
| `unavailable-cooldown` | 失败后冷却时间 | 30～60 秒 |
| `realtime-max-rows` | 实时查询最大行数 | 200～500 |

### 9.3 环境变量建议

外部库配置通过环境变量或本地 `.env` 注入：

- `SUB2API_DB_ENABLED`
- `SUB2API_DB_URL`
- `SUB2API_DB_USERNAME`
- `SUB2API_DB_PASSWORD`
- `SUB2API_DB_CONNECT_TIMEOUT`
- `SUB2API_DB_QUERY_TIMEOUT`
- `SUB2API_DB_REALTIME_QUERY_TIMEOUT`
- `SUB2API_DB_POOL_SIZE`
- `SUB2API_DB_MIN_IDLE`
- `SUB2API_DB_BATCH_SIZE`
- `SUB2API_DB_MAX_BATCHES_PER_RUN`
- `SUB2API_DB_UNAVAILABLE_COOLDOWN`
- `SUB2API_DB_REALTIME_MAX_ROWS`

要求：

- 密码不得写入 Git；
- 不得写入测试代码；
- 日志中不得输出完整 URL 中的账号密码；
- 配置类不得在 `toString()` 中输出密码；
- 生产环境建议启用 TLS。

## 10. 连接池和查询资源限制

### 10.1 主库连接池

建议：

- 最大连接数：8～12；
- 最小空闲：2；
- 连接超时：5 秒；
- 最大生命周期：5 分钟；
- keepalive：1 分钟。

具体值必须根据部署规格和 PostgreSQL 连接上限调整。

### 10.2 外部只读连接池

建议：

- 最大连接数：2～4；
- 最小空闲：1；
- 连接超时：3～5 秒；
- `readOnly=true`；
- `autoCommit=true`；
- 初始化失败不 fail-fast；
- 外部库失败进入冷却窗口；
- 应用关闭时关闭连接池。

### 10.3 查询约束

所有外部查询必须：

- 使用参数绑定；
- 有超时；
- 有最大行数；
- 有明确的排序；
- 有明确的时间范围；
- 尽量命中索引；
- 禁止 `SELECT *`；
- 禁止无界分页；
- 禁止把外部用户输入直接拼接到 SQL；
- 禁止在持有主库事务时执行外部查询。

## 11. 定时同步设计

### 11.1 同步目标

定时同步只同步“需要长期保留、需要历史对比、需要本地预警计算”的外部数据。

首选同步数据：

- `usage_logs` 增量用量明细；
- 需要本地缓存的平台用户摘要；
- 需要本地缓存的账号/分组倍率；
- 需要做趋势分析的渠道指标。

默认不落本地：

- 支付订单明细；
- 运维错误日志；
- 临时页面查询结果；
- 可随时从外部库实时读取且不需要历史的数据。

### 11.2 同步游标

本地主库需要专门的同步游标记录。

建议逻辑表：

- `sub2_sync_cursor`：保存不同同步任务的游标；
- `sub2_sync_run`：保存每轮同步的执行状态。

游标至少包含：

- 同步任务编码；
- 数据对象；
- 最后处理的 ID；
- 最后处理时间；
- 最后成功时间；
- 最后失败时间；
- 连续失败次数；
- 当前状态；
- 错误信息摘要。

`usage_logs` 使用 `id` 游标，不使用 `created_at` 作为唯一游标。原因是时间字段可能重复或乱序，主键游标更适合增量同步。

### 11.3 首轮初始化

首次启用同步时：

1. 查询外部表当前 `MAX(id)`；
2. 把该值保存为初始游标；
3. 默认只同步初始游标之后的数据；
4. 需要历史回灌时单独开启回灌任务；
5. 回灌任务不得与正常增量任务同时写同一批数据。

### 11.4 分页和批处理

建议参数：

- 单批 1000～2000 条；
- 每批一个短事务；
- 单轮最多 10～20 批；
- 单批完成后立即更新本地游标；
- 单轮完成后更新同步任务状态；
- 单批失败时不要推进游标；
- 下一轮从最后成功的游标继续。

禁止：

- 一次查询几十万条；
- 单轮执行时间无限延长；
- 使用偏移量分页做大数据量扫描；
- 全部数据都放在内存中后再写库。

### 11.5 幂等策略

每个本地镜像表必须至少具备一种幂等约束：

- 外部主键唯一；
- `source_system + external_id` 唯一；
- 内容哈希唯一；
- 业务唯一键唯一。

推荐：

- 外部数据使用 `source_system`、`external_id` 标识来源；
- 使用 PostgreSQL `INSERT ... ON CONFLICT DO UPDATE`；
- 更新时间字段要与本批数据一起写入；
- 重复执行同一批数据不能产生重复记录；
- 重复执行同一批数据不能重复触发通知。

### 11.6 重叠执行保护

定时同步必须防止上一轮未结束时下一轮再次启动。

单实例部署可先使用内存运行标记；多实例部署必须使用数据库级锁：

- PostgreSQL advisory lock；
- 任务状态表条件更新；
- 唯一运行记录约束。

第一版如果仍然单实例，也必须保留“任务正在执行”状态，不能依赖调度器线程池自己保证。

### 11.7 重试和失败记录

建议：

- 单批最多重试 2～3 次；
- 重试间隔指数退避；
- 连续失败达到阈值后进入冷却；
- 每轮记录失败状态、失败时间、失败原因摘要；
- 错误信息截断后保存，避免超过数据库字段长度；
- 不把数据库密码、完整连接串写入错误信息；
- 外部库连续失败时，页面显示“外部数据暂不可用”，而不是持续阻塞请求。

### 11.8 同步与预警的关系

同步和预警不要合成一个大事务。

推荐顺序：

```text
外部只读查询
→ 读取一批数据
→ 本地短事务写入镜像表
→ 更新同步游标
→ 触发或等待预警计算
→ 本地保存预警状态
→ 通知模块发送通知
```

预警计算可以：

- 在同步批次提交后异步触发；
- 或由独立定时任务读取本地镜像后计算。

不要让同步任务直接持有外部数据库连接去调用通知服务或长时间执行业务逻辑。

## 12. 实时读取设计

### 12.1 适用范围

实时读取适用于：

- 页面需要展示的外部用户信息；
- 当前分组和倍率增强信息；
- 当前订单或错误摘要；
- 机器人按用户发起的即时查询；
- 预警详情中的辅助上下文。

不适用于：

- 大批量历史数据；
- 高频轮询；
- 跨多表的大范围统计；
- 需要长时间事务的数据处理。

### 12.2 查询约束

实时查询必须满足：

- 单次查询超时 2～3 秒；
- 最大返回行数 200～500；
- 必须有明确过滤条件；
- 必须有明确排序；
- 不使用无界 `LIKE '%...%'` 作为主过滤条件；
- 不读取敏感字段；
- 外部库故障时快速失败，不无限重试。

### 12.3 降级策略

建议把外部查询结果分为以下状态：

- `DISABLED`：外部数据源未启用；
- `UNAVAILABLE`：连接失败或处于冷却窗口；
- `TIMEOUT`：查询超时；
- `SUCCESS`：查询成功；
- `EMPTY`：查询成功但没有数据。

业务层必须区分“外部库没有数据”和“外部库不可用”。

不能把连接失败简单当成空列表返回，否则预警会产生错误判断。

### 12.4 缓存策略

适合短 TTL 缓存的数据：

- 用户身份摘要；
- 用户余额；
- 分组名称和倍率；
- 代理到期信息。

不建议缓存：

- 错误详情；
- 实时订单状态；
- 与安全相关的敏感数据；
- 时间敏感度极高的状态。

缓存建议：

- TTL 10～60 秒；
- 外部数据失败时可以使用最后一次已知数据，但必须标记数据陈旧；
- 缓存 key 必须包含外部数据源和查询条件；
- 不允许无限期缓存。

### 12.5 实时查询与主库事务

实时查询外部库时：

- 不开启本地默认事务；
- 不把外部查询放在主库 Repository 方法中；
- 不把外部查询结果直接绑定到本地 Entity；
- 查询完成后再用独立短事务写本地数据。

## 13. 预警链路设计

### 13.1 推荐链路

```text
外部只读查询 / 本地镜像数据
→ 预警条件计算
→ 生成预警结果
→ 本地主库保存预警状态
→ 通知模块读取本地状态
→ 邮件 / QQ 通知
```

预警计算模块不得直接依赖通知 Adapter。

### 13.2 定时预警

适用于：

- 用户余额预警；
- 用量异常预警；
- 渠道倍率变化；
- 代理到期；
- 外部数据库不可用。

推荐流程：

1. 定时任务读取本地镜像或外部只读库；
2. 计算预警条件；
3. 将预警状态写入本地主库；
4. 发布领域事件；
5. 通知模块在事务提交后消费事件；
6. 记录通知发送结果。

### 13.3 实时预警

适用于用户在页面或机器人中主动查询的场景。

规则：

- 外部查询有短超时；
- 预警结果不跨库事务；
- 外部库不可用时明确告知用户；
- 不允许因为外部库不可用而重复发送大量告警；
- 同一预警应有去重键和冷却时间。

### 13.4 预警去重

每条预警至少需要：

- 预警类型；
- 资源键；
- 严重级别；
- 触发时间；
- 去重键；
- 冷却截止时间；
- 当前状态；
- 最后通知时间。

去重键示例由业务定义，但必须稳定，不能每次随机生成。

## 14. 事务和一致性

### 14.1 事务规则

- 主库可以使用本地 `@Transactional`。
- 外部只读库不使用默认事务管理器。
- 不在一个事务中同时写入两个数据库。
- 不在主库事务中等待外部 HTTP 或外部 JDBC 查询。
- 外部查询完成后再开启主库短事务。
- 长耗时采集不能包在一个大事务中。
- 通知发送不在数据库事务中执行；应在事务提交后异步处理。

### 14.2 一致性模型

允许的模型：

- 外部数据最终同步到本地；
- 本地保存同步时间、游标和状态；
- 读取方可以看到数据陈旧标记；
- 失败后可以重试；
- 重复执行保持幂等。

不允许的模型：

- 依赖分布式事务；
- 依赖两阶段提交；
- 本地写成功后假设外部已同步；
- 外部写成功后假设本地已保存。

### 14.3 跨库操作失败处理

如果外部读取成功、本地写入失败：

1. 不推进同步游标；
2. 增加失败次数；
3. 下一轮重新拉取同一批数据；
4. 依赖幂等约束避免重复。

如果本地写入成功、通知发送失败：

1. 本地预警状态保留；
2. 记录通知失败；
3. 下一轮重试通知；
4. 不重新执行外部采集。

## 15. 故障降级矩阵

| 故障场景 | 主业务 | 外部关联功能 | 处理 |
|---|---|---|---|
| 主库不可用 | 不可用 | 不可用 | 健康检查失败，停止写入，记录错误 |
| 主库慢查询 | 受影响 | 可能受影响 | 连接池、慢 SQL、超时告警 |
| 外部库未配置 | 正常 | 显示未启用 | 不创建外部连接池 |
| 外部库连接失败 | 正常 | 降级 | 记录失败，进入冷却窗口 |
| 外部查询超时 | 正常 | 返回超时状态 | 不无限重试 |
| 外部表结构变更 | 正常 | 相关功能失败 | 记录字段/查询错误，通知维护者 |
| 外部只读权限不足 | 正常 | 相关功能不可用 | 记录权限错误，提示授权 |
| 同步任务失败 | 正常 | 使用上次成功数据 | 保留游标，下一轮重试 |
| 通知发送失败 | 正常 | 预警仍保留 | 本地记录失败，异步重试 |

外部库任何故障都不能阻止应用启动，也不能让主库进入不可用状态。

## 16. 安全要求

1. 外部库必须使用专用只读账号。
2. 只读账号只授予实际需要的表 SELECT 权限。
3. 不授予 `INSERT`、`UPDATE`、`DELETE`、`TRUNCATE`、DDL 权限。
4. 不使用应用主账号连接外部库。
5. 密码仅通过环境变量或密钥管理系统注入。
6. 不把密码提交到 Git。
7. 日志不输出密码和完整凭证。
8. 查询只取必要字段。
9. 不读取外部库中的密码哈希、TOTP 密钥、明文 API Key。
10. 外部查询结果返回前按业务需要脱敏。
11. 生产环境建议启用 SSL/TLS。
12. 外部库连接串和账号不得直接展示到前端页面。
13. 所有外部 SQL 必须参数化。
14. 禁止把用户输入拼接到表名、列名或 SQL 片段。
15. 外部数据导出功能必须单独做权限校验。

## 17. 可观测性

### 17.1 日志

同步日志建议包含：

- 同步任务编码；
- 数据对象；
- 当前游标；
- 本批数量；
- 成功/失败状态；
- 耗时；
- 连续失败次数；
- 错误摘要。

实时查询日志建议包含：

- Reader 名称；
- 查询类别；
- 耗时；
- 是否命中缓存；
- 是否降级；
- 不记录完整敏感参数。

### 17.2 指标

建议增加：

- 主库连接池活跃连接数；
- 外部库连接池活跃连接数；
- 外部查询成功/失败次数；
- 外部查询超时次数；
- 外部库冷却次数；
- 同步批次数；
- 同步记录数；
- 同步失败次数；
- 最后成功同步时间；
- 外部数据陈旧时间。

### 17.3 健康检查

健康检查应区分：

- 主库健康状态；
- 外部库配置状态；
- 外部库最近一次连接状态；
- 外部库是否处于冷却窗口；
- 最近一次同步是否成功。

外部库不健康不应导致整个应用健康状态直接变为 DOWN，除非业务明确要求。可以在健康详情中标记为 `OUT_OF_SERVICE` 或自定义状态。

## 18. 测试策略

### 18.1 单元测试

不连接真实数据库时，使用接口 Fake 或 Mock 测试：

- 采集范围选择；
- 采集间隔计算；
- 连续失败退避；
- 到期账号判断；
- 同步游标推进；
- 外部不可用降级；
- 预警去重；
- 事务边界外的调用顺序。

### 18.2 配置测试

验证：

- 外部库未配置时应用正常启动；
- 外部库配置不完整时给出明确日志；
- 外部连接池为只读；
- 外部库默认关闭；
- 主库配置不受外部配置影响；
- Flyway 只执行主库。

### 18.3 数据访问测试

外部库测试使用独立测试容器或测试 schema：

- 只读账号不能写入；
- `usage_logs` 增量游标正确；
- 时间窗口左闭右开；
- 用户软删除过滤正确；
- 分组倍率查询正确；
- 订单汇总不受明细 LIMIT 影响；
- 查询超时和连接失败可被捕获；
- 外部库关闭时不创建连接池。

### 18.4 集成测试

至少覆盖：

- 同步一批数据后游标推进；
- 重复同步同一批数据不重复写入；
- 外部库失败时主库功能仍可用；
- 外部库恢复后冷却窗口解除；
- 通知失败不回滚本地预警状态。

没有真实外部库时，普通 `mvn test` 不应依赖外部数据库。外部联调测试应使用 `contract` tag 或独立 profile。

## 19. 推荐实现顺序

### 阶段 1：配置边界

1. 创建 `Sub2ReadOnlyDataSourceProperties`；
2. 创建 `Sub2ReadOnlyJdbc`；
3. 验证未配置时应用可启动；
4. 验证外部连接池只读；
5. 验证主库 MyBatis-Plus 和 Flyway 不受影响。

### 阶段 2：最小只读查询

1. 选择一个最简单的只读查询；
2. 使用 `JdbcTemplate` 和明确超时；
3. 返回只读 record；
4. 增加配置关闭、连接失败和成功测试；
5. 不接业务页面。

### 阶段 3：同步基础设施

1. 设计 `sub2_sync_cursor`；
2. 设计 `sub2_sync_run`；
3. 实现同步游标读取和更新；
4. 实现重叠执行保护；
5. 实现失败记录和冷却。

### 阶段 4：用量增量同步

1. 读取当前最大 ID；
2. 按 `id > cursor` 拉取；
3. 按批写入本地；
4. 更新游标；
5. 验证幂等和失败重试。

### 阶段 5：其他外部 Reader

按优先级迁移：

1. 用户身份；
2. 分组倍率；
3. API Key 用量；
4. 订单；
5. 错误日志；
6. 代理和渠道监控。

### 阶段 6：预警

1. 从本地镜像或外部 Reader 计算；
2. 保存本地预警状态；
3. 事务提交后发事件；
4. 通知模块消费；
5. 增加去重和冷却。

## 20. 验收标准

### 20.1 数据源

- [ ] 只有两个 PostgreSQL 数据源。
- [ ] 主库可读写并执行 Flyway。
- [ ] 外部库只读且不执行 Flyway。
- [ ] 外部库默认关闭。
- [ ] 外部库未配置时应用正常启动。
- [ ] 外部库连接失败不影响主库启动。
- [ ] 两个连接池名称可区分。
- [ ] 外部连接池设置 `readOnly=true`。
- [ ] 外部连接池在应用关闭时正确释放。

### 20.2 ORM 和 Mapper

- [ ] MyBatis-Plus 只连接主库。
- [ ] 外部库没有 MP Entity。
- [ ] 外部库没有 MyBatis Mapper。
- [ ] 外部 SQL 只存在于 `integration.sub2db`。
- [ ] 主库 Mapper 不会扫描外部 Reader。
- [ ] Controller 不直接依赖外部 Reader。

### 20.3 同步

- [ ] 使用游标增量。
- [ ] 单批有大小限制。
- [ ] 单轮有批数限制。
- [ ] 失败不推进游标。
- [ ] 重复执行幂等。
- [ ] 有重叠执行保护。
- [ ] 有失败次数和最后成功时间。
- [ ] 有同步状态查询能力。

### 20.4 实时查询

- [ ] 有查询超时。
- [ ] 有最大返回行数。
- [ ] 参数全部绑定。
- [ ] 外部库不可用时有明确状态。
- [ ] 不把连接失败伪装成空结果。
- [ ] 高频查询支持短 TTL 缓存。

### 20.5 事务和安全

- [ ] 不存在跨库事务。
- [ ] 外部查询不持有主库事务。
- [ ] 通知发送不在数据库事务中。
- [ ] 外部只读账号权限最小化。
- [ ] 密码不进入 Git 和日志。

## 21. 禁止事项清单

- 禁止使用动态数据源路由替代明确的数据访问边界。
- 禁止使用 `@DS` 一类注解在业务方法上隐式切换数据库。
- 禁止把 Sub2API 外部表注册成 MyBatis-Plus Entity。
- 禁止外部库执行 Flyway。
- 禁止在外部库执行写操作。
- 禁止跨库事务。
- 禁止在主库事务中查询外部库。
- 禁止把外部 Reader 直接注入 Controller。
- 禁止无超时查询外部库。
- 禁止无 `LIMIT` 的实时查询。
- 禁止 `SELECT *`。
- 禁止字符串拼接 SQL。
- 禁止记录密码和完整连接凭证。
- 禁止把外部库故障当成“没有数据”。
- 禁止在同步失败时继续推进游标。
- 禁止不设幂等约束就让同步重试。
- 禁止把预警状态只保存在外部库或内存中。

## 23. 最终结论

RelayOps 采用：

```text
本地主库
+ MyBatis-Plus
+ Flyway
+ 默认本地事务
+ 独立 HikariCP
```

以及：

```text
Sub2API 外部只读库
+ 独立 JdbcTemplate 查询网关
+ 只读连接池
+ 懒初始化
+ 查询超时
+ 失败冷却
+ 不执行 Flyway
+ 不参与默认事务
+ 不注册 MP Mapper
```

所有外部数据接入必须遵守：

```text
外部读取
→ 数据转换
→ 本地短事务保存
→ 预警计算
→ 事务提交后通知
```

不允许用一个事务同时覆盖外部库和本地库。
